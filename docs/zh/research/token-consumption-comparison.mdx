# Token 消耗对比调研（调研缓存）

> 2026-11-13 · 调研缓存文档，不是用户指南。我们把参考实现（pi、Claude Code、Codex、Cursor）的上下文管理与 TNT 逐项对照，结论沉淀在这里，供后续优化引用。

## 背景

我们在一次 66 分钟的真实 agent 会话里测得：

| 指标 | 实测值 |
| --- | --- |
| 请求次数 | 533 |
| 累计输入 | 112,302,767 token |
| 缓存命中输入 | 111,616,768（99.4%） |
| 单次平均输入 | 210,699 |
| 上下文增长 | 11,664 → 294,191 |

缓存命中率高意味着钱不是主要问题；问题在 token 总量与时长：533 次请求、每次平均 210K 上下文、单次约 7 秒，排满就是一小时。同样的任务，参考实现给出的请求次数和单次体积都要小一个量级。

## 根因排序

1. **没有工具输出淘汰（microcompact）**——最大头。上下文里大部分是历史工具输出，Read 单次可塞 25K token，几十次读写后只涨不降；我们唯一的瘦身手段是压缩，而压缩阈值在 1M 窗口下是 800K，永远够不着。
2. **压缩阈值跟着窗口走**。Claude Code 用绝对阈值+按窗口分级 buffer；codex 直接配模型级 token 上限。窗口大不等于工作集该大。
3. **压缩后保留太多**。我们保留 16%（1M 窗口 ≈ 160K），pi 只留 20K，codex 留摘要+全部用户消息（20K 预算）。
4. **轮数虚高**。一次会话里 65 次无效工具调用 + 18 次执行失败，每次失败都是一整轮全量重发。
5. Read/Bash 截断上限偏大（50K/100K 字符 vs codex 10K token、Claude Code 30K 字符）。

## 优化路线（按顺序落地）

1. 工具输出淘汰：超过阈值（如窗口 40%）时，把最近 N 个之外的工具结果替换成 `[Old tool result content cleared]`，原文留在 session.jsonl。
2. 压缩阈值改绝对值+分级：`compactAt = min(0.8×窗口, 绝对上限)`；`retainRatio` 下调或加绝对保留上限。
3. 工具输出上限下调：Read 100K→50K 字符、Bash 50K→30K 字符，或按 token 计。
4. 并行工具调用：一次多个 tool_calls 并行执行，权限提示适配。
5. 按工具粒度失败熔断：同一工具连续失败 N 次把诊断注入最后一条 tool result 并降级。

预期：同样的任务 token 总量降到 1/3–1/5，时长降到十几分钟量级。

## 事实核查备注

- DeepSeek 官方定价页确认现役 `deepseek-flash`（DeepSeek-V4.1-Flash-1017）上下文 1M，所以我们的预设 `contextLength: 1000000` 不是错值；问题在压缩策略与淘汰缺失，不在窗口声明。
- cursor 侧证据来自解包内核的静态分析（无 source map，引用为 byte offset），已另行归档。
